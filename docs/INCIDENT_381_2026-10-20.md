# Juno proposal 381: incompatible programme claim actions

Proposal 381 passed its vote but failed during execution on 20 October 2026.
Cosmoot generated `distribution.withdraw_delegator_reward` messages inside
`execute_admin_msgs`. The deployed programme contract does not accept the
`distribution` variant. This was an implementation and validation failure.

The failure is unrelated to the later rule-review size correction: proposal 381
was submitted on 15 October. Its recorded content is immutable.

The exact downloaded binary and original proposal payload are retained as test
fixtures. The regression runs that binary's execute entry point and reproduces
the recorded parser error before any host call, storage access or emitted
withdrawal message. None of the 37 withdrawals executed through this proposal.
This targeted reproduction is not a successful end-to-end execution test.

## Why existing checks missed it

The JavaScript tests compared the generated payload with the same assumed
message format. They did not run it through the deployed programme binary.
Preflight checked authority, code ID, pause state, withdrawal destination and
current delegations. Those checks did not establish the accepted execution schema.
The transaction simulation covered `MsgSubmitProposal`, which stores the proposal;
it did not establish that the embedded contract messages would execute after voting.
Browser tests used synthetic successful submission responses.

## DAO DAO documentation and deployed authority

The official [SubDAO guide](https://docs.daodao.zone/dao-management/subdaos/what)
defines the parent's admin authority. Its
[Admin Execute guide](https://docs.daodao.zone/dao-management/subdaos/act-on-behalf-of-subdao)
documents executing actions on behalf of a SubDAO.
In the [v2.4.0 interface](https://github.com/DA0-DA0/dao-contracts/blob/v2.4.0/packages/dao-interface/src/msg.rs),
`ExecuteAdminMsgs` is distinct from `ExecuteProposalHook`. The
[core implementation](https://github.com/DA0-DA0/dao-contracts/blob/v2.4.0/contracts/dao-dao-core/src/contract.rs)
checks the stored admin for the former, and an enabled proposal module for the latter.

The deployed programme's internal admin is the Juno governance module, matching
proposal 381's outer sender. Its enabled proposal module is
`juno172fvxz9806ae6rjecd09trgrzkcl0026y088ev3lsyg88gmpr7cs764evh` (code 4054),
and voting module is `dao-voting-cw4` 2.4.0, code 4055. The outer admin-execute
route was valid; the inner message representation caused the failure.

The official DAO DAO UI's
[ManageStaking implementation](https://github.com/DA0-DA0/dao-dao-ui/blob/d207ac875e6dae23469223687f6fbbc022852f01/packages/stateful/actions/core/actions/ManageStaking/index.tsx)
constructs staking reward withdrawals as Stargate `MsgWithdrawDelegatorReward`
messages with explicit delegator and validator addresses. That implementation
provides a reference for a replacement, not proof that a new proposal has
successfully executed. Reading these version-specific sources and checking the
actual contract interface should have preceded release of the original generator.

## Containment candidate

New programme claims, publication/revision/finalization of programme execution
reviews, native submission and additional funding are blocked in the candidate.
Historical review decoding, public evidence, votes and receipt recovery remain
available. The proposal view displays the chain's `failed_reason` as plain text.
The full submission/funding browser regression now uses a text-only rule decision,
so it cannot be mistaken for proof of claim execution.

This candidate still requires CI, integration and the deliberate website release.
There is no replacement claim authorized by this change. A future replacement
needs exact contract-schema and binary checks, decoded signer-bound messages,
and end-to-end execution evidence for the programme and chain handlers. Passing
a submission simulation alone is insufficient.
